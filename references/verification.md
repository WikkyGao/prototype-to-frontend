# 浏览器级验证与修复循环

目标：生成的代码不仅在浏览器里能打开，而且**和原型长得一致**。流程分四级门槛，逐级执行，任何一级失败都阻断交付。

## 1. 构建级门槛（必过）

按 lockfile 选包管理器（pnpm-lock → pnpm，yarn.lock → yarn，否则 npm）：

```bash
npm run build        # 必须退出码 0
npm run lint         # 有 lint script 才跑；报错必须修
```

- 新项目首次验证前确认依赖已安装（`npm install`）
- build 失败 → 修复 → 重跑；连续 3 次修不过，停下来向用户汇报错误现场

## 2. dev server 启动

```bash
# 后台启动（Bash run_in_background），固定端口便于截图，被占用则 +1 重试
npm run dev -- --port 5199
```

**ready 判定**：读后台任务输出，出现 `Local:`、`ready in`、或端口可访问（`curl -s -o /dev/null -w "%{http_code}" http://localhost:5199` 返回 200）才算启动完成，不要盲等固定秒数。Next/Nuxt 用各自 dev 脚本；uni-app/Taro 用 `dev:h5` 脚本编译 H5 端再验证 H5 地址。

## 3. Playwright 截图

### 3.1 工具优先级

1. 当前环境挂载了 playwright / browser-use 相关 skill 或 MCP 工具 → 优先用它们（能做点击等交互）
2. 否则用 CLI（首次需装浏览器内核）：

```bash
npx -y playwright install chromium   # 一次性
npx -y playwright screenshot --viewport-size="1440,900" --full-page \
  "http://localhost:5199/users" .ptf-shots/users.png
```

3. 都不可用 → 降级构建级验证，**明确告知用户降级及原因**

### 3.2 截什么

- **每个已实现路由**一张全页截图（视口宽度按原型画布：后台 1440、移动端原型 375）；**关键页**另补交互态
- **截图前必须等异步内容渲染完成**：等表格/列表行真实出现（`page.waitForSelector` 行选择器或 `networkidle`；CLI 用 `--wait-for-timeout` 给足数据加载时间）。路由返回 200 就截图是无效证据——v0.3.0 实测中曾截到整表空白
- **语言环境与原型对齐**：截图前检查 UI 语言（如 Element Plus 默认英文 locale 会留下 "Total 23"/"Select" 残留），必要时配置 zh-cn
- **关键交互态（仅关键页）**：设计意图 interactions 中的主要项（tab 切换后、弹窗打开、下拉展开、表单校验报错）——用技能或临时脚本操作后补截；只有静态截图能力时，交互态验证降级为代码走查并在交付时说明
- 截图统一放 `.ptf-shots/`（工作目录临时目录，交付后可清理）

uni-app/Taro 的 H5 端路由带 hash（`/#/pages/users/index`），截图 URL 按框架实际格式来。

## 4. 对比（仅关键页；模型目视，非像素 diff）

**页面分级**（防成本失控，也防"自己生成自己评"的噪声）：

- **关键页** = 入口/首屏页、含主要交互（表单提交、tab、弹窗）的页、用户圈选时标注重点的页
- **长尾页** = 其余页面 → 只验"路由可渲染"（HTTP 200 + 截图留存），**不做对比与修复循环**；交付时截图照常展示

对关键页，把**基线截图**与**实现截图**并排 Read，按清单检查：

| 检查项 | 可接受 | 不可接受 |
|---|---|---|
| 布局结构 | 间距 2-8px 级偏差 | 分区缺失/错位（如侧栏变顶栏） |
| 关键组件 | 图标风格细节差异 | 表格/表单/卡片整块缺失 |
| 配色风格 | 个别灰阶差异 | 主色/色系不对 |
| 文案内容 | 中英文标点差异 | 标题、按钮、字段 label 文字错误 |
| 数据 | mock 值与原型示意值不同 | 字段本身缺失或多余（臆造） |

判断口径是**结构性一致**，不是像素级复刻——原型本来就是示意稿。拿不准的差异先归为"待确认"，不强行"修复"。

**证据纪律**：对比结论只以**落盘的截图文件**为准——Read 截图亲眼确认后再下结论，不得用"断言通过/代码看起来对"替代视觉核验，也不得让交付报告的声明超出截图能证明的范围（v0.3.0 实测中曾出现"报告称一致、截图状态列空白"的自相矛盾）。

## 5. 修复循环（仅关键页）

```
对比 → 问题清单（页/问题/严重度）→ 修复 → 只重截受影响页 → 再对比
```

- **默认最多 2 轮**；用户在确认环节可改轮数
- 每轮开始前列出本轮要修的问题清单（让过程可追溯）
- 2 轮后仍不一致的项**不要继续盲修**：截取基线与实现的对比图，连同差异原因分析（如"原型为示意、与 UI 库默认行为冲突"）进入交付的待确认清单
- 修复只动生成的文件；改到公共配置/依赖时须重新确认 build + lint

## 6. 栈差异与降级

| 栈 | 验证方式 |
|---|---|
| React/Vue3/Next/Nuxt | 浏览器级（上述全流程） |
| uni-app / Taro | 编译 H5 端做浏览器级；交付时说明"小程序端仅构建验证（`build:mp-weixin` 等通过）" |
| Flutter | 构建级：`flutter analyze` + `flutter build web`（或 apk）；向用户说明无浏览器对比 |
| 原型基线缺失（方式2起不了服务） | 降级构建级 + 代码走查（按设计意图 structure 逐项核对组件存在性），交付时说明 |

## 7. 交付前收尾

- 最终实现截图用 Read **展示给用户**（必须，这是用户验收的直观依据）
- 停掉后台 dev server（记录启动命令让用户自己起）
- 清理 `.ptf-baselines/`、`.ptf-shots/` 等临时目录（或询问用户是否保留对比图）
